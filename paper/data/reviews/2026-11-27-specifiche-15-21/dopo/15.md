## Specifica
1. **Accesso a Docker dai test.** Maven gira dentro un container, quindi i test devono poter avviare altri container e raggiungerne le porte. La soluzione si sceglie e si descrive in `docs/sviluppo.md` con i suoi rischi (per esempio: chi ha accesso al socket di Docker controlla Docker). Deve funzionare **sia su macOS con Docker Desktop sia in GitHub Actions su Linux**, e le due prove vanno entrambe riportate. `./verify.sh` continua a richiedere sull'host solo Docker.
2. **Test di integrazione di esempio** in `carddemo-parity`, con Testcontainers: avvia PostgreSQL, crea una tabella temporanea propria, scrive, rilegge, la elimina. Dimostra il meccanismo; non introduce schema.
3. **Stessa immagine di `compose.yaml`.** Il test ricava l'immagine dal servizio `db` di `compose.yaml` (percorso risolto dalla radice del repository, non dalla cartella del modulo) e **avvia proprio quella**, tag e digest compresi: non una seconda costante da tenere allineata. Un'asserzione verifica che l'immagine del container effettivamente avviato coincida.
4. **Mai saltati in silenzio.** Se dentro Maven Docker non è raggiungibile, il test di integrazione fallisce e `./verify.sh` termina con codice diverso da 0, entro un tempo limite. Nessuna annotazione o proprietà che disabiliti i test quando Docker manca.
5. **Regressioni di `verify.sh` come comando.** Le garanzie verificate a mano sulla PR #20 diventano uno script versionato, `quality/regressioni-verify.sh`, che per ciascun caso applica la mutazione, esegue `./verify.sh` con un limite di tempo, verifica codice di uscita **e messaggio** atteso, e ripristina lo stato anche in caso di errore. Casi: un test rotto; `repackage` rimosso da un modulo con un jar eseguibile della corsa precedente presente; `id` che fallisce; `docker` che fallisce; test di integrazione con Docker non raggiungibile dentro Maven. Non si includono attacchi in cui uno strumento restituisce dati falsi ma ben formati (regola "Fin dove arriva la sfiducia negli script" in `CLAUDE.md`). Lo script non fa parte di `./verify.sh` né della CI obbligatoria: si esegue a richiesta.

## Invarianti da preservare
- Le garanzie di `./verify.sh` già esistenti (build, test, cancellazione degli output, jar eseguibili unici, `id`, `docker`).
- `./smoke.sh` e il suo job di CI restano verdi e non vengono modificati.

## Criteri di accettazione (verificabili)
- [ ] Da clone pulito, solo Docker, **su macOS**: `./verify.sh` termina con 0; il log mostra l'avvio del container PostgreSQL e il test di integrazione eseguito e non saltato (`Skipped: 0`).
- [ ] **In GitHub Actions**: il job `verify` è verde sulla PR e il suo log mostra la stessa cosa (collegamento all'esecuzione nella PR).
- [ ] Immagine: cambiando in `compose.yaml` il solo tag, e separatamente il solo digest, con valori validi di un'altra versione, il test avvia l'immagine cambiata (prova che la legge davvero); con un valore inesistente, `./verify.sh` fallisce.
- [ ] Docker non raggiungibile **dentro Maven**, con Docker funzionante sull'host per avviare il container di build: `./verify.sh` termina con codice diverso da 0 entro il limite, e il fallimento è quello del test di integrazione.
- [ ] `./quality/regressioni-verify.sh` termina con 0 (tutti i casi rilevati) e lascia `git status` pulito; alterando lo script di verifica in modo che un caso non venga più rilevato, termina con codice diverso da 0 (provato per almeno un caso, descritto nella PR).
- [ ] Dopo `./verify.sh`, riuscito o fallito, non restano container di test in esecuzione (comando ed esito nella PR).
- [ ] `smoke` verde in CI; il diff tocca solo il perimetro dichiarato.
